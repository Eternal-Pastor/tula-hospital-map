# Карта прикрепления Тульской области

Локальный сайт на HTML, CSS и JavaScript. Две отдельные страницы используют одну подложку Яндекса. Серверная логика приложения не нужна; для пересчёта времени запускаются отдельные локальные OSRM.

## Пользователь и разработчик

Ветка `codex/user-developer-views`.

- `index.html` — пользовательская страница, открывается по адресу http://localhost:8765/. Режимы: длительность пути, зоны прикрепления, нагруженность. Прикрепление на 1 000 жителей: меньше 700 — зелёный; от 700 до 1 000 включительно — жёлтый; больше 1 000 — красный; отсутствующее значение — серый.
- `developer.html` — прежняя страница с настройками, резервными копиями, методикой, исходными таблицами и техническими пояснениями. При каждом открытии вводится код `immortaL` (с учётом регистра). До верного ввода прикладные скрипты не загружаются. Это клиентский экран входа, не серверная авторизация: исходники и код доступны тому, у кого есть файлы сайта.
- Переходов между страницами нет: пользователь открывает `index.html`, разработчик — напрямую `developer.html`. Пользовательская таблица и карточка содержат название, прикрепление на 1 000 жителей, площадь зоны (км²) и плановую пропускную способность (посещений / смену). Подсказка ячейки: «Больница - время в минутах», для выбранного способа передвижения.

В `viewer-data.js` встроен проверенный снимок полного расчёта 5 км: 38 больниц, 1 942 ячейки, 3 884 ответа для машины и пешего режима. Он подготовлен из `backups/hospital-project-osrm-2026-10-24.json`, без изменения оригинала. При открытии распаковывается gzip, проверяется SHA-256 и сразу показываются готовые данные; запросы к маршрутизатору и геокодеру не нужны. Снимок содержит готовые зоны, показатели больниц и исходные значения времени; линии маршрутов исключены, адресные списки для просмотра не нужны. Все исходные файлы и полная резервная копия сохранены отдельно.

Пропуски заполняются тем же методом по соседним измеренным ячейкам своей больницы. При изменении сетки измеренные ячейки базовой сетки 5 км также остаются донорами. На пользовательской странице пометки ≈ и методические пояснения скрыты по требованию; математическая обработка не меняется. На странице разработчика оценки по-прежнему отмечены. Площадь зоны вычисляется по полному сферическому полигону, с вычитанием внутренних колец.

В `viewer-config.js` указан предоставленный публичный ключ JavaScript API. Ограничения разрешённых адресов задаются в кабинете Яндекса. Пользовательские дорасчёты хранятся в отдельной IndexedDB, привязанной к контрольной сумме снимка; хранилище разработчика и его настройки не изменяются. Вид карты, транспорт и размер сетки запоминаются отдельно. Новые расчёты используют только localhost:5000 и localhost:5001, четыре запроса одновременно; остановка сохраняет полученные ответы, продолжение не повторяет их.

Для обновления встроенных данных разработчик экспортирует полную копию с покрытием и завершённым расчётом 5 км, затем из корня проекта запускает `node work/build_viewer.cjs ПУТЬ_К_КОПИИ.json` и `python work/package_site.py`. Генератор проверяет контрольную сумму, соответствие больниц/координат/границ и полноту ответов. `hospital-map.html` — самостоятельная пользовательская страница. ZIP включает обе страницы и все необходимые ресурсы; `developer.html` открывается отдельно.

## Эксперимент OSRM

Источник расчёта — **локальные OSRM**, только **машина и пешком**, без текущих пробок. Ключ маршрутов Яндекса не нужен. Подложка карты остаётся Яндексом; адреса и зоны восстанавливаются локально. Старые ответы Яндекса сохраняются в резервных копиях разработчика отдельно.

Нажмите «Рассчитать всю область»: будут обработаны все ячейки для обоих способов. Уже готовые ответы повторно не запрашиваются. В корне проекта есть `local-routing/README.md`, `compose.yaml`, `Prepare-OSRM.ps1` и `Start-OSRM-WSL.ps1`. Docker и дорожные данные не устанавливаются сайтом автоматически.

Кэш разделён по провайдеру и URL: времена Яндекса не подставляются в результаты OSRM. Привязка к дороге ограничена радиусом 1 км. Время от исходной точки ячейки до привязки не добавлено. Дата ответа означает момент расчёта по графу, а не наличие сведений о текущих пробках. Источник, URL сервиса и расстояния привязки входят в резервную копию разработчика.

Публичные службы: [FOSSGIS](https://routing.openstreetmap.de/about.html), [API OSRM](https://project-osrm.org/docs/v5.24.0/api/). Дорожные данные — © OpenStreetMap contributors. Далее описаны общие функции сайта и сохранённый режим Яндекса.

## Запуск

### Полная резервная копия и перенос (страница разработчика)

На панели карты нажмите **«Резервные копии» → «Скачать полную копию»**. JSON версии 2 включает найденные и неподтверждённые адреса, готовые векторные снимки, маршруты обоих провайдеров, пользовательские координаты и настройки OSRM/сетки/фильтров. Ключи API не экспортируются. SHA-256 проверяет целостность файла, но не удостоверяет его автора. Максимальный размер импортируемого файла — 100 МБ.

На другом устройстве откройте ту же версию сайта, выберите файл, проверьте показанные количества и нажмите «Восстановить выбранную копию». До этого данные не меняются. «Объединить» сохраняет найденные адреса вместо ошибок и более свежие маршруты; настройки берутся из выбранной копии. «Восстановить проект целиком» возвращает состав данных выбранной версии. Перед применением текущий проект автоматически сохраняется в браузере; кнопка «Скачать копию до последнего изменения» позволяет получить его отдельно. Загрузка данных IndexedDB выполняется одной транзакцией. Настройки браузера сохраняются после успешной записи данных. Старые копии версии 1 также читаются, но не содержат контрольной суммы и настроек доступности.

Готовые векторы переносятся вместе с адресами: если входные данные совпадают, они восстанавливаются без пересчёта. Если исходный набор отличается, интерфейс предупреждает об этом; несовместимые снимки пересчитываются по принятым адресам. Маршрутизация и геокодер при импорте и перезагрузке не вызываются. Ключ подложки карты на новом устройстве вводится отдельно.

Готовый самостоятельный файл `hospital-map.html` расположен рядом с папкой `hospital-map` в `outputs`. Его можно перенести отдельно: стили, код и исходные значения уже внутри. Открытие из файла подчиняется ограничениям ключа Яндекса, описанным ниже.

Для варианта с отдельными исходниками:

1. Запустите `start-localhost.cmd` двойным щелчком. Браузер откроет `http://localhost:8765/`. Окно сервера оставьте открытым; остановка — Ctrl+C. Используется Python из установленного Codex, либо Python 3 из системы. Приложение остаётся статическим: сервер только отдаёт файлы и доступен на этом компьютере.
2. Нажмите «Подключить Яндекс Карты».
3. Введите ключ **JavaScript API**. Для маршрутов введите отдельный ключ **API получения деталей маршрута** в третье поле. Второе поле — необязательный ключ геокодера; для маршрутов он не нужен.
4. Нажмите «Подключить карту». Геокодер при подключении не проверяется и не вызывается; сохранённые адреса восстанавливаются локально.
5. Если нужен новый поиск и лимит геокодера доступен, включите «Разрешить новый поиск адресов» и нажмите «Найти все адреса и построить зоны». Поиск охватит все 37 больниц независимо от текущего фильтра. У каждой зоны свой цвет. Кнопка «Найти организации на карте» отдельно находит положения учреждений. В карточке больницы по-прежнему доступен поиск порциями по 20 адресов.

Ключи не зашиты в файлы проекта. Они сохраняются в браузере только при выборе «Сохранить ключи на этом устройстве и подключать карту автоматически». Сохранённые ключи можно удалить в настройках карты. В экспорт настроек ключи не попадают.

### Ограничения запуска из файла

Внутренние данные подключаются обычным `data.js`, без запросов к локальным JSON-файлам. Таблицы, фильтры и расчёт цветов работают при открытии через `file://`.

Доменное ограничение ключа Яндекса проверяет HTTP Referer. У страницы, открытой из файла, обычного HTTP Referer нет. Если настройки вашего ключа требуют домен, Яндекс может отклонить такую страницу. Это ограничение внешнего API, а не потребность приложения в серверной логике. Не отключайте ограничения ключа без понимания условий его использования. Возможность запуска карты из файла нужно проверить с активным ключом вашего аккаунта.

При запуске через локальный HTTP-адрес в ограничении по HTTP Referer ключа укажите только `localhost`, без протокола и порта. Поле ограничения по IP-адресам оставьте пустым. Открывайте страницу именно через `http://localhost:8765/`. Изменения ограничений могут применяться до 15 минут. Внешний хостинг приложение самостоятельно не использует.

## Доступность и временные зоны

В панели «Доступность больниц» включите «Показать время в пути» или нажмите «Разбить зоны локально». Можно выбрать все сохранённые зоны или больницу, выбранную в списке. Ячейки обрезаются исходным контуром, включая отверстия; сохраняют закрепление за больницей и не перераспределяют дома. Начальная точка находится внутри фрагмента ячейки. Шаг: 250 / 500 / 1000 / 2000 / 5000 / 10000 м; линейный масштаб приближён для широты Тульской области. Максимум 2500 фрагментов; при превышении увеличьте шаг или выберите одну больницу. Построение и объединение выполняются в Web Worker, отрисовка — небольшими порциями.

**Модельная оценка · без API** доступна сразу при наличии сохранённой точки больницы. Расстояние по сфере между точкой ячейки и больницей умножается на сценарную поправку длины пути и делится на скорость. Для транспорта добавляется ожидание. Начальные допущения: машина 35 км/ч, пешком 4,5 км/ч, транспорт в движении 18 км/ч, длина пути / прямая = 1,3, ожидание 10 минут. Все параметры редактируются; это не измеренные скорости и не дорожные маршруты. Прямые пунктирные линии показывают направления. Реки, мосты, закрытые проезды, остановки, пересадки и расписания модель не учитывает. Автомобильные пробки в этом режиме также не учтены.

**Реальные маршруты Яндекса** запрашиваются только кнопками, по координатам, без геокодера. Если в настройках задан отдельный ключ маршрутов, используется HTTP API `https://api.routing.yandex.net/v2/route`: параметры `apikey`, `waypoints` в порядке широта/долгота и `mode=driving|walking|transit`. Время отправления не задаётся: оценка соответствует моменту обработки запроса. Время пути — сумма `steps[].duration`; геометрия — `steps[].polyline.points`. Устаревшее `waiting_duration` не прибавляется. Тип информации о пробках из ответа сохраняется и отображается в карточке ячейки. Отказ HTTP API не переключает расчёт скрыто на другой продукт.

Без отдельного ключа новые маршруты не запрашиваются: кнопка «Подключить API маршрутов» открывает настройки и выделяет третье поле. Автоматического перехода к маршрутизатору JavaScript API нет. Ранее сохранённые пути JS API продолжают отображаться. Чтобы не вводить ключи после перезагрузки, явно включите «Сохранить ключи на этом устройстве и подключать карту автоматически» перед подключением; иначе ключи используются только в текущем сеансе.

За нажатие выполняется не более 3, 30 или 90 запросов, последовательно, с паузой минимум 1,1 секунды. Одна ячейка требует 3 запросов. Ошибка или таймаут 30 секунд останавливает порцию; автоматических повторов нет. Остановка вручную сохраняет полученное. Статус `FAIL` HTTP API или пустой успешный ответ JS API хранится как «Путь не найден»; ошибки доступа, сети и формата ответа не кэшируются как недостижимость. На карте отображаются линии, возвращённые Яндексом. В среднем режиме показываются все три пути. CSV содержит также `provider` и `traffic_type`.

Проверка 23.10.2026 после подключения отдельного HTTP API: из страницы на `http://localhost:8765/` успешно получены и локально сохранены три маршрута для одной ячейки — машина, пешком и общественный транспорт. Ранее новый ключ отвечал HTTP 401; после активации запросы прошли. Ключи в файлах проекта не сохранены. Запрос и разбор ответа сверены с [форматом запроса](https://yandex.ru/maps-api/docs/router-api/request.html) и [форматом ответа](https://yandex.ru/maps-api/docs/router-api/response.html).

При проверке 21.10.2026 подложка работала, а первый запрос маршрута вернул `scriptError`. Причину отказа этот ответ не раскрывает. Подтверждены логика адаптера на контролируемых ответах и обработка отказа в браузере; получение успешных реальных маршрутов с текущим ключом не подтверждено. Проверяйте доступ к маршрутизации и её квоту в кабинете Яндекса. Геокодер для этой проверки не нужен.

Диагностика 23.10.2026: ошибка воспроизведена для двух координат с `reverseGeocoding:false`. Не загрузился ресурс `api-maps.yandex.ru/services/route/2.0/`; SDK передаёт `apikey` и временный `token`. Сам `scriptError` не доказывает превышение квоты или неверный ключ. Ошибка теперь показывает способ передвижения и адрес ресурса без параметров авторизации. В консоль выводятся только имена параметров и разрешённые значения `lang`, `rll`, `rtm`, `results`; ключи и токены исключены.

Пользователь подтвердил `Sec-Fetch-Dest: script`, `Sec-Fetch-Mode: no-cors`, `Referer: http://localhost:8765/`; консоль Floorp сообщила `OpaqueResponseBlocking` и `NS_ERROR_DOM_NETWORK_ERR`. Затем тот же набор параметров `callback`, `lang`, `token`, `rll`, `rtm`, `results`, `apikey` был проверен отдельным HTTP-запросом без сохранения и вывода секретов. Сервис ответил **HTTP 403**, `Content-Type: application/json; charset=utf-8`, тело: `{"statusCode":403,"error":"Forbidden","message":"Invalid api key"}`. Это объясняет блокировку: вместо ожидаемого JavaScript-ответа сервис возвращает JSON с отказом авторизации. Успешное отображение подложки не подтверждает доступ ключа к маршрутизации. Из этого ответа нельзя отличить неподходящий доступ к продукту от ограничений ключа; это следует уточнить в кабинете или поддержке Яндекса.

Дополнительная HTTP-проверка через `fetch` удалена: она сама может блокироваться CORS и смешивать две разные ошибки. Прямая навигация по URL с ключом и временным токеном также не используется. Интерфейс направляет к исходному запросу типа `script/js` в F12 → «Консоль» и «Сеть», не сохраняет и не экспортирует полный URL и не предлагает выключать ORB/CORS. Автоматических повторов и дополнительных диагностических запросов нет. Геокодер, адресный кэш и готовые зоны не сбрасываются. После настройки доступа ключа можно повторить минимальную порцию из трёх маршрутов для одной ячейки.

Среднее — арифметическое трёх времён с равными весами 1/3. Если хотя бы одного реального маршрута нет, среднее отсутствует. Это не среднее по жителям и не отдельный маршрут. Цвета: зелёный ≤15 минут, жёлтый >15–30, оранжевый >30–60, красный >60, серый — данных нет или путь не найден. Это условная шкала удобства, не норматив медицинской доступности. Переключатель «Временные зоны» объединяет ячейки одного диапазона внутри одной больницы. Точность ограничена сеткой, найденной частью зоны и выбранной точкой приёма.

Без координат больницы её ячейки серые. Задайте проверенные широту и долготу в карточке организации; юридический адрес может не совпадать с терапевтическим приёмом. Центр зоны автоматически не подставляется вместо больницы.

Реальные времена, геометрии и даты ответа сохраняются в IndexedDB и входят в резервную копию «Адреса и зоны». Ключ кэша содержит организацию, начало, конец и режим; смена точки больницы или точки ячейки исключает повторное использование прежнего пути. При перезагрузке запросы не отправляются, сетка восстанавливается локально. Снимки времени не обновляются автоматически и могут устареть. Параметры модели и выбор режима сохраняются в настройках этого браузера. CSV времени содержит источник, координаты, дату и параметры модельного сценария. Для одной ячейки доступны четыре значения в диалоге.

Официальные интерфейсы: [параметры маршрута](https://yandex.ru/dev/jsapi-v2-1/doc/ru/v2-1/ref/reference/IMultiRouteParams), [модель мультимаршрута](https://yandex.ru/dev/jsapi-v2-1/doc/ru/v2-1/ref/reference/multiRouter.MultiRouteModel).

## Интерфейс

### Зоны обслуживания больниц

В поле «Цвет на карте» можно выбрать «По больнице закрепления». Каждая организация получает свой цвет; режим численности остаётся доступен отдельно.

Кнопка «Найти все адреса и построить зоны» запускает поиск всех ещё не проверенных адресных групп: до четырёх запросов одновременно, с общим интервалом запуска около 200 мс (до пяти запусков в секунду). Очередь чередует больницы, чтобы крупная организация не задерживала появление остальных зон. Обновление границ запрашивается по ходу поиска примерно раз в 750 мс. Само разбиение выполняется в Web Worker отдельно от интерфейса и сетевых запросов. Одновременно считается один снимок данных; накопившиеся промежуточные задания заменяются последним. Пока новый результат не готов, показана предыдущая проверенная версия зон. Объекты карты добавляются небольшими порциями, неизменившиеся слои не пересоздаются. Неизменившиеся контуры берутся из кэша, одинаковые адресные запросы объединяются, включая ещё выполняющиеся. Скорость и примерное оставшееся время выводятся над картой. Искусственной паузы 300 мс после каждого ответа больше нет. Это ускоряет загрузку, но не увеличивает суточную квоту внешнего API. Поиск включает организации без численности и сбрасывает строку поиска; автоматически включается окраска по больнице. В раскрывающемся списке «Цвета построенных зон» можно выбрать нужную больницу.

Общий индикатор показывает проверенные, найденные и неподтверждённые адреса, а также число построенных зон. Кнопка «Остановить поиск» останавливает выдачу новых заданий и отменяет ожидание незавершённых запросов. Уже полученные результаты сохраняются, отменённые адреса остаются в очереди; штатная остановка не показывается как ошибка. Повторное нажатие большой кнопки продолжает оставшуюся очередь без повторения найденных адресов. Неподтверждённые адреса повторяются отдельно в карточках больниц.

В источнике 10 179 адресных групп и 10 154 уникальных текста адресов. Полный поиск может занять длительное время и превысить суточную квоту API. При ошибках доступа, сети или квоты обработка приостанавливается; текущий адрес остаётся в очереди. Каждый результат сохраняется в IndexedDB до обновления счётчика поиска. После перезагрузки найденные адреса, неподтверждённые результаты и положения больниц восстанавливаются. Кнопка продолжает только оставшиеся адреса. Контуры появляются после нахождения минимум трёх различных ориентиров, не лежащих на одной прямой.

В карточке больницы раздел «Зона обслуживания» показывает количество исходных правил домов, уникальных улиц и населённых пунктов, найденных и ненайденных ориентиров. Кнопка поиска обрабатывает следующие 20 ещё не проверенных адресов. Поиск можно остановить с сохранением уже полученных результатов. Ненайденные адреса не мешают перейти к следующей порции; для них есть отдельный список с причинами и кнопка повторной проверки.

Все правила одной улицы внутри больницы собраны в одну точку. Если вместо улицы геокодер вернул только центр города или района, такой результат не добавляется как подтверждённый ориентир. Её карточка сохраняет диапазоны, чётность и ссылки на строки DOCX. Один и тот же адрес у разных больниц не объединяется в одно назначение. В источнике 37 зон организаций и подразделений, 10 831 правило, 10 154 уникальных текста адресов; 22 текста встречаются у разных организаций. Последнее само по себе не доказывает пересечение домов.

Отдельная таблица «Зоны больниц: улицы и дома» показывает объединённые адреса, домовые правила и другие больницы с тем же текстом улицы. Исходная таблица «Адресные правила» сохраняет все строки без объединения. Чтобы видеть зоны организаций без численности, включите соответствующий флажок в списке.

Зона отображается полупрозрачным векторным полигоном с пунктирной границей. Начальные оболочки строятся по найденным адресным ориентирам. Их перекрытия разделяются ячейками Вороного: принадлежность ячейки задаёт ближайший закреплённый адресный ориентир. Результат ограничивается исходной оболочкой своей больницы. Контуры обновляются после следующих порций поиска. Нужны минимум три различные точки, не лежащие на одной прямой; при меньшем числе контур не создаётся. В карточке и всплывающем окне указаны число и доля найденных адресов. Это доля адресных групп, а не доля населения или площади.

Контур приблизительный: ориентиры улиц и населённых пунктов не задают границы отдельных домов. Геометрия не подтверждает принадлежность каждого дома и не охватывает ещё не найденные адреса. Внутренние области разных зон не пересекаются. Координаты обрабатываются в целочисленной сетке около сантиметра; после разделения добавляется служебный зазор менее метра, который исключает также касание контуров и артефакты округления. Для фактических границ нужен GeoJSON или подготовленная геометрия закреплённых домов. Загруженный контур заменяет автоматически построенный для той же организации и резервирует свою территорию. Если загруженные контуры разных больниц конфликтуют, спорные фрагменты удаляются из обоих отображений; число конфликтов показано под картой. Исходный GeoJSON сохраняется без изменений.

Разбиение рассчитывается по всем больницам, поэтому поиск в списке, выбор больницы и фильтры не меняют границы соседей. При совпадении координат ориентиров разных больниц соответствующая ячейка остаётся неокрашенной: общая точка центра улицы не позволяет разделить конкретные диапазоны домов. Прикрепление домов и численность из исходных данных не перераспределяются. Возможны отдельные фрагменты и отверстия внутри зоны. Если геометрический расчёт не завершился, контуры скрываются с объяснением; исходные перекрывающиеся оболочки не показываются в качестве замены.

Под картой переключатели «Векторные зоны» и «Адресные точки» управляют слоями независимо. По умолчанию зоны включены, адресные точки скрыты. Цвет зоны соответствует выбранному режиму окраски. Найденные геокодером ориентиры сохраняются локально. Производные контуры автоматически пересчитываются по сохранённым координатам после загрузки страницы; повторных запросов к геокодеру для них нет.

- **Карта** — основное представление. Поиск, показатели и список организаций находятся слева; карточка выбранной организации — справа.
- **Таблицы** — отдельное представление на той же странице: организации, все исходные записи терапевтических участков, адресные правила, плановая мощность, справочное население. Есть фильтры, поиск, постраничный просмотр и экспорт CSV.
- **О данных** — методика, ограничения источников и экспорт/импорт локальных настроек.

## Значение цветов

Показатель по умолчанию — прикреплённые взрослые на 1 000 жителей выбранного города или района:

`прикреплённые взрослые / всё население выбранной территории × 1 000`

Это относительная численность. Знаменатель содержит всё население, поэтому показатель не является долей охвата взрослых, клинической нагрузкой или вероятностью обращения.

Дополнительные режимы: сумма прикреплённых и средняя численность на запись терапевтического участка.

Границы зелёной, жёлтой и красной групп — 33,3-й и 66,7-й процентили распределения по всем организациям с доступными значениями. Используется линейная интерполяция с округлением границ до двух знаков. Фильтр поиска не меняет границы. Равные значения получают одинаковый цвет. Отсутствие данных отображается серым.

По умолчанию учитывается только категория «Взрослые». Смешанную категорию «Взрослые, дети» можно включить отдельным флажком. Исходная таблица участков сохраняет все строки независимо от этого переключателя.

Население взято из сообщения пользователя. Город и район не суммируются. Предварительную связь с территорией можно изменить в карточке. Там же можно исправить население; это изменит значение территории для всех связанных организаций. Прикрепление больше населения — повод проверить сопоставимость границ и периодов, а не признак перегрузки.

Положения больниц заданы предоставленным пользователем файлом координат. В исходных данных отсутствуют готовые границы, индивидуальные координаты домов, терапевтическая мощность и спрос. Приложение строит приблизительные контуры по найденным адресам и не рассчитывает реальную перегрузку.

Адресные правила не разворачиваются автоматически в индивидуальные дома: текст «все дома», диапазоны и чётность сохраняются в таблицах. На карте отображаются ориентиры найденных улиц и населённых пунктов с подписью точности. Геокодирование отправляет адреса в Яндекс, результаты сохраняются в локальном хранилище и включаются в отдельную резервную копию адресов и зон.

## Подготовленные границы и координаты

Можно импортировать GeoJSON `FeatureCollection` с геометрией `Point`, `Polygon` или `MultiPolygon`. Поле `properties.organizationId` обязательно и должно совпадать с ID из таблицы организаций или её карточки. Порядок координат GeoJSON — **долгота, широта**. Кольца полигонов должны быть замкнуты. Импорт заменяет предыдущий набор объектов.

Необязательные свойства: `name`, `source`, `kind`. В `source` укажите происхождение границы или координаты. Пример структуры с пустым набором (без вымышленных объектов):

```json
{"type":"FeatureCollection","features":[]}
```

Координаты конкретной организации также можно ввести вручную в её карточке. Порядок полей там — **широта, долгота**, как подписано в форме. Пользовательские координаты и GeoJSON включаются в экспорт локальных настроек.

## Долгий расчёт и временные сетевые ошибки

Построение границ больше не выполняется в основном потоке страницы. Поиск, кнопки и таблицы остаются доступны во время расчёта. Статус под картой показывает, когда обновление ещё идёт; поиск адресов может закончиться раньше расчёта границ. Проверка отсутствия наложений выполняется в фоновом расчёте и сохраняется для каждой отображаемой версии.

Одна попытка геокодирования ждёт до 30 секунд. При временном сетевом сбое, таймауте или HTTP 5xx выполняются максимум три попытки с короткой паузой. Все обращения, включая повторы, проходят через общий ограничитель частоты. HTTP 401, 403 и 429 автоматически не повторяются. Если попытки исчерпаны, адрес остаётся непроверенным, чтобы следующий запуск мог его обработать. Ошибка отмены при нажатии «Остановить поиск» считается штатной остановкой.

После изменения `zones.js`, `territories.js`, `zones-worker.js` или vendored-библиотек запускайте `work/package_site.py`: он обновляет встроенный исходник Web Worker (`zones-worker-source.js`), самостоятельный HTML и ZIP. В готовой поставке всё уже включено, запуск браузера не требует сборки или CDN.

## Сохранение результатов

IndexedDB хранит координаты адресных ориентиров, их точность, принадлежность больнице, неподтверждённые проверки и найденные положения организаций. При восстановлении приложение связывает эти записи с актуальными правилами домов из исходного набора. Неизвестные адреса, некорректные координаты и устаревшие запросы организаций пропускаются. Контуры восстанавливаются из координат, цвет и пользовательские GeoJSON — из локальных настроек.

Хранилище относится к конкретному браузеру и origin. Используйте тот же адрес **http://localhost:8765/**: другой порт, `127.0.0.1`, другой браузер или приватный режим имеют отдельное хранилище. Очистка данных сайта может удалить результаты.

В разделе «О данных» кнопка **«Скачать адреса и зоны»** сохраняет резервный JSON с результатами и настройками; **«Загрузить адреса и зоны»** переносит его в другой браузер или восстанавливает копию. Ключей API в копии нет. Старый экспорт настроек остаётся отдельным форматом. При ошибке записи виден статус и доступна кнопка повторного сохранения.

Для автоматического подключения Яндекс Карт выберите в настройках **«Сохранить ключ на этом устройстве и подключать карту автоматически»**. При следующих загрузках используется сохранённый ключ, а адресный поиск и тестовый запрос геокодера автоматически не запускаются. Без сохранённого ключа адреса и таблицы восстанавливаются сразу; подложка появляется после подключения карты. Интернет нужен для загрузки Яндекс Карт.

Сохранение действует начиная с этой версии. Результаты прежней версии, оставшиеся только в памяти старой вкладки, не были записаны в хранилище и автоматически не переносятся.

## Проверка ключей

1. Войдите в https://developer.tech.yandex.ru/.
2. Подключите JavaScript API для карты. При отдельном продукте геокодирования подключите API Геокодера и используйте выданный ему ключ во втором поле.
3. Проверьте статус сервиса и активацию ключей; она может занимать до 15 минут.
4. Проверьте разрешённые домены и подходящий тариф в кабинете.
5. Если видна карта, но тестовый адрес не найден, доступ к геокодированию ещё не подтверждён. Ошибка HTTP 403 / Invalid api key требует проверки ключа, его сервиса, активации и ограничений.

### Если в консоли Invalid API key

Сообщение `(Yandex Maps JS API): Invalid API key` относится к ключу **JavaScript API**, введённому в первое поле. Отдельный ключ API Геокодера вводится во второе поле и не заменяет ключ карты. При этом подложка карты всё ещё может появляться.

Для каждого ключа откройте соответствующий продукт в кабинете Яндекса и проверьте подключение продукта, статус активации и ограничения. Ошибка `403 / Invalid api key`, полученная и прямым запросом к сервису, означает отказ авторизации до обработки адреса; смена адресных данных такую ошибку не исправит. По одному этому ответу нельзя отличить неверный продукт от неактивного ключа или неподходящих ограничений.

Если у ключа обязательно ограничение по HTTP Referer, открытие через `file://` может не подходить. При открытии через HTTP имя хоста должно быть разрешено у ключа; `localhost` и `127.0.0.1` — разные значения и указываются отдельно. Обход ограничений API приложение не выполняет.

Отдельный Isochrone API не используется. Временные зоны получаются объединением ячеек по диапазонам времени, а не точными изолиниями дорожного графа. Приложение не выполняет оптимизацию.

Официальная документация:

- JavaScript API 2.1: https://yandex.ru/dev/jsapi-v2-1/doc/ru/
- HTTP Геокодер: https://yandex.ru/maps-api/docs/geocoder-api/request.html
- Ограничения ключей: https://yandex.ru/maps-api/docs/js-api/limit.html

### Восстановление готовых векторов

Готовые полигоны сохраняются в той же IndexedDB отдельным снимком `geometry:zones-v1`, включая отверстия и сведения о разделении зон. При открытии приложение сначала читает сохранённые адреса и готовые векторы, затем проверяет совпадение исходных точек и импортированных границ. Если они совпадают, полигоны загружаются сразу, без Worker и геокодера. Для старого хранилища, содержащего только адреса, один раз выполняется локальное построение и запись снимка. Запись пустого стартового состояния до чтения IndexedDB не выполняется. Статус показывает число сохранённых векторных зон; после восстановления в легенде появляется «Восстановлено готовых векторных зон локально». Выбранная организация сохраняется вместе с настройками, поэтому режим «Выбранная больница» не теряет её после перезагрузки. Подложка Яндекса по-прежнему требует подключения JavaScript API; если ключ не сохранён, подключите карту вручную. Снимок векторов входит в резервную копию адресов и зон.

### Прогресс восстановления

Над картой отображаются четыре этапа: чтение IndexedDB, восстановление или локальный пересчёт полигонов, подключение подложки, отрисовка. Чтение и расчёт без известного объёма показываются неопределённым индикатором; искусственные проценты не используются. При отрисовке отображается реальное число добавленных фрагментов полигонов из общего количества и процент этого этапа. До подключения карты отображается ожидание, а при ошибке — её причина. После завершения остаются отметка 100% и количество восстановленных адресов и зон. Фрагменты относятся к видимым зонам с учётом фильтров; отключённый слой указан отдельно.

### Диагностика второго этапа на больших наборах адресов

Worker передаёт текущую операцию, обработанное количество и больницу: подготовка, поиск пересечений, ячейки Вороного, объединение по больницам, разделение границ и итоговая проверка. Сообщения прогресса не считаются завершением задания. Интерфейс раз в секунду показывает общее время и время без обновлений. Отсутствие новых сообщений не доказывает зависание: одна операция объединения может быть длительной. После 30 секунд без сообщений появляется безопасный перезапуск расчёта; он прекращает только Worker, затем использует сохранённые адреса без геокодирования. Границы полигонов для повторных проверок кэшируются в Worker; вычисление рамок не использует разворачивание больших массивов аргументов.

### Обобщённая модель пропускной способности

По уточнению пользователя плановые посещения в смену из формы 30 используются как общая пропускная способность больницы, без детализации по специальностям. В карточке показана сумма строк «Мощность, всего» сопоставленных подразделений; внутренняя разбивка по видам поликлиник к итогу не прибавляется. Связь подразделений с больницей и её зоной требует проверки. Это плановый предел в рамках симуляции.

Для загрузки нужны: число смен в день (по филиалам, если графики различны), число рабочих дней выбранного периода, спрос в посещениях за тот же период либо сценарная частота посещений на прикреплённого человека. При известной годовой частоте r и числе рабочих дней W: D_день = N × r / W. При одинаковом режиме подразделений C_день = C_смена × S, загрузка = D_день / C_день. Для разных режимов следует суммировать C_смена филиала × S филиала. Фактические обслуженные посещения дают использование мощности; для оценки неудовлетворённого спроса дополнительно нужны обращения, отказы и очередь. До задания этих величин численность прикреплённых не интерпретируется как поток посещений.

### Ускорение объединения соседних адресных ячеек

Для ячеек Вороного одной больницы сначала удаляются парные внутренние рёбра и сшивается оставшаяся граница; затем она обрезается исходной зоной. Это заменяет одну большую операцию объединения тысяч соседних полигонов. Сшивание учитывает раздельные компоненты и отверстия; проверка отсутствия наложений и зазор между больницами сохранены. При неоднозначном наборе рёбер используется резервное объединение пакетами по 24 ячейки, с предварительной обрезкой. Индикатор показывает обработанные ячейки, рёбра или проход и количество пакетов внутри конкретной больницы. Новых запросов геокодера нет.

На синтетическом случае из 8100 соседних ячеек одной больницы среди 37 организаций предыдущий расчёт занял около 36 секунд, сшивание границ — около 0,3 секунды на тестовой машине; суммарная площадь совпала. Это не гарантия времени на другом устройстве или конкретном кэше. Сценарий включён в регрессионную проверку вместе с отверстиями, раздельными компонентами, пересечениями и совпадающими адресами.


### Координаты больниц из файла пользователя

Сценарий доступности по выбору пользователя: ячейки **5 км**, источник «Реальные маршруты Яндекса», оценка на момент отправки запроса без задания будущего выезда. Для машины используется возвращённое время с пробками, если оно доступно. Старые настройки размера сетки и источника один раз заменяются этим сценарием; последующие изменения пользователя сохраняются. Сохранённые ответы остаются снимками на момент получения. Новые маршрутные запросы выполняются только по кнопке.

В `sources/hospital-coordinates.csv` сохранён предоставленный файл: 37 явных пар «широта, долгота» и одна ссылка Рассвета на координаты Плехановской амбулатории. Подготовка данных проверяет все 38 ID, числовые координаты, региональные пределы и отсутствие циклических ссылок. Координаты и адрес объекта встроены в `data.js`, отдельная загрузка CSV и геокодер при открытии сайта не нужны. Плавская ЦРБ: **53.719074, 37.291045**.

Один источник положения используется для маркера, выбора больницы, конечной точки маршрута и модельной оценки времени. Старые геокодированные положения и ручные координаты из предыдущей версии не перекрывают новый файл. Новая явная ручная поправка сохраняется вместе с версией исходных координат; кнопка в карточке возвращает точку из файла. При изменении исходных координат старые поправки перестают применяться. Адрес объекта, координаты и отметки о совпадениях доступны в карточках; координаты также включены в таблицу организаций и её CSV-экспорт.

У Рассвета и Плехановской амбулатории одна точка по прямому указанию в файле. Одоевская ЦРБ и её филиал № 1 также получили одинаковые координаты из файла; это отмечено в карточках и подсказках маркеров. Организации, численность, мощность и адресные зоны не объединяются. Файл координат сохраняется без исправления этих совпадений.

Кэш адресов жителей и готовые векторы сохраняются. Маршрутный кэш включает конечные координаты, поэтому ответы для прежней точки больницы не используются при изменении назначения. Реальные маршруты по-прежнему запрашиваются только по кнопке. Сценарная оценка доступна локально без API-запросов.


### Полное покрытие области

Перед изменениями скачайте полную копию через кнопку «Резервные копии». «Заполнить пробелы» дополнительно сохраняет состояние до расчёта в IndexedDB: его можно скачать там же кнопкой «Скачать копию до последнего изменения». Если сохранение не удалось, заполнение не запускается. Исходный снимок `geometry:zones-v1` сохраняется отдельно от расширенного `geometry:coverage-v1` и входит в каждую последующую копию. Импорт показывает состав копии и проверяет SHA-256 до применения, затем предлагает объединение или полное восстановление.

Заполнение использует встроенную границу Тульской области из OpenStreetMap (отношение 81993, версия 135 от 21.09.2026; © OpenStreetMap contributors, ODbL). Запросов геокодера, маршрутизатора и загрузки границ при расчёте нет. Граница находится в `region.js`; исходный GeoJSON — в `sources/tula-boundary.geojson` проекта, воспроизводимая упаковка — `work/prepare_region.py`.

Существующие зоны обрезаются по границе области, их принадлежность внутри области сохраняется. Незанятое пространство распределяется по ближайшей больнице по прямой: диаграмма Вороного по координатам больниц, с поправкой долготы cos(54°). Это геометрическое приближение, без дорог и изохрон. При совпадении координат новый фрагмент получает первая больница по ID; исходные зоны всех организаций сохраняются. Расширение не добавляет жителей, посещения или мощность.

На карте каждая больница показана единым расширенным контуром с одинаковой заливкой: внутренний стык исходной и добавленной части удалён объединением геометрии. Общие границы разных больниц соприкасаются, искусственный зазор исходного режима убран. Отдельные компоненты остаются компонентами одной зоны; соединение их коридорами изменило бы распределение соседних больниц. Исходные и добавленные геометрии хранятся в копии для аудита, но отдельными слоями не рисуются.

Перед показом проверяются остаточные пробелы, выход за область и попарные наложения. Целочисленное округление координат около 1 см создаёт узкие численные погрешности на стыках; допуск каждой суммарной проверки — 1e-7 квадратного градуса (около 730 м² на всю область). Большие ошибки останавливают заполнение. На предоставленной копии Floorp: 37 исходных зон, 38 расширенных; заполнено 13,08% площади, расчёт около 5 с на тестовой машине. Остаточные численные площади: пробелы около 122 м², наложения около 70 м², выход за границу около 8 м² по всей области; это округление тонких стыков. Эти метрики сохраняются в снимке.

Переключатель «Полное покрытие области» возвращает исходный режим без удаления расширенных векторов. При повторном включении и перезагрузке готовое покрытие восстанавливается из IndexedDB без расчёта, если адреса, координаты больниц и версия границы совпадают. После изменения входных данных покрытие пересчитывается в Worker. Индикатор показывает этап, количество проверенных зон/пар и время с последнего обновления; интерфейс остаётся доступен. Фильтры могут скрывать зоны — для полного отображения покажите все организации и очистите поиск.

Сетка 5 км на предоставленном полном покрытии даёт 1942 фрагмента ячеек. Маршруты по ним запрашиваются только отдельной кнопкой; прежние 703 результата остаются в копии. Для новых точек сетки может потребоваться новый расчёт.


### Упрощённый полный расчёт и заполнение времени

В основной панели остаются размер сетки (5, 10 или 20 км) и кнопка «Рассчитать всю область». Источник — локальные OSRM localhost:5000/5001. Одно нажатие готовит полное покрытие, строит сетку всей области и рассчитывает сразу машину и пеший режим четырьмя параллельными запросами. Размеры сетки выбраны для полного регионального обзора без сотен тысяч объектов. Выбор способа передвижения в легенде меняет только отображаемый результат и не ограничивает расчёт. Источники, модельные параметры, число запросов за порцию, отдельный запуск сетки и выбор больницы для расчёта убраны из основного интерфейса. Таблицы, карточки больниц и перенос резервных копий сохранены.

Уже сохранённые ответы повторно не запрашиваются. Прогресс показывает фактическое число обработанных пар «ячейка, способ». Во время работы доступна остановка; полученные ответы сохраняются пакетами по 50. После остановки следующий запуск продолжает оставшиеся. При ошибке сохранения ответы остаются в памяти и следующая попытка сначала сохраняет их без повторного HTTP-запроса. Сетка и отрисовка работают в фоне или короткими порциями; удаление старых полигонов также порционное.

Для каждой ячейки и каждого способа передвижения сначала используется найденный ответ OSRM. Если ответа нет или OSRM вернул NoSegment/NoRoute, время оценивается по четырём ближайшим ячейкам с реальным ответом в зоне той же больницы: среднее с весами 1/расстояние². Известные значения, включая нулевые, не изменяются. Оценённые ячейки не используются как доноры; результат не зависит от порядка обработки. Если в зоне больницы нет ни одного реального ответа, используется отдельная резервная оценка по расстоянию до её больницы (скорости 35 и 4,5 км/ч, коэффициент пути 1,3). Без координат больницы время не выдумывается: полный запуск сообщает о необходимых координатах.

Оценки обозначены ≈ в сводке, подсказках и карточке ячейки; в карточке видны источник и расстояние до ближайшего донора. Заполнение времени не доказывает наличие дороги или маршрута. Исходные NoSegment/NoRoute сохраняются без изменения, оценка не записывается в маршрутный кэш как реальный ответ, линия для неё не создаётся. Значения восстанавливаются локально из сетки и сырых маршрутов при загрузке страницы и переносе копии, без новых запросов.

На исходной копии с 1942 ячейками: автомобиль — 1258 реальных + 684 по соседям; пешком — 1733 реальных + 209 по соседям. Для обоих режимов все 1942 ячейки имеют время, резервная оценка по расстоянию не понадобилась. Снимок перед изменением интерфейса: backups/before-interface-simplification-2026-10-24.json. Новая сетка 10 км также проверена полным запуском из браузера: 768 ячеек, оба режима заполнены и сохранены. Резервная копия с маршрутами остаётся совместима; вычисленные оценки отделены от исходных ответов.
